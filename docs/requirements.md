# 배치 서비스 요구사항

사용자가 업로드한 노트북을 정해진 일정에 실행하고, 실제 실행 결과에 대한
분석 리포트를 결과 노트북 마지막에 추가한다. 전체 데이터 분석 시스템의
부가 서비스이며 사용자 진입점은 `prj_re`다.

2026-10-12 인터뷰 기준. 아래 확정 범위와 별개로 세부 구현안은
[서비스 설계 초안](design.md), 기존 구현과의 차이는
[연동 계약 검토](integrations.md)에서 관리한다.

## 확정 범위

| 항목 | 합의 내용 |
| --- | --- |
| 소유권 | 사용자별 구분. 프로젝트 소속 없음 |
| 사용자 진입점 | 기존 분석 시스템 `prj_re`. 배치 서비스는 내부 API 제공 |
| 입력 | 출처 제한 없이 `.ipynb` 파일 업로드. 초기에는 코드 셀만 취급 |
| 버전 | 등록 당시 원본 보존. 수정 파일은 새 버전 또는 별개 등록으로 구분 |
| 실행 단위 | 배치 하나에 노트북 하나. 노트북 간 의존성 없음 |
| 실행 환경 | Executor BATCH 풀 사용. Jupyter 커널 명시 |
| 파라미터 | 초기에는 주입하지 않음. 고정 코드를 그대로 실행 |
| 일정 | 일회성, 간격, 일·주·월 반복, Cron, 시작·종료 기간 등 일반 일정 |
| 시간대 | 기본 `Asia/Seoul` |
| 초기 상태 | 비활성 등록 후 사용자가 명시적으로 활성화. 수동 실행 가능 |
| 실행 겹침 | 건너뛰기, 대기, 병렬 실행 중 배치별 선택 |
| 겹침 판단 | 코드 실행 종료 기준. 리포트 작성은 다음 실행을 막지 않음 |
| 놓친 일정 | 생략, 최근 1회, 제한된 보충 실행 중 선택 |
| 실행 재시도 | 정책은 보류. 초기에는 상태만 기록하고 자동 재실행하지 않음 |
| 리포트 책임 | `prj_re`에 독립 리포트 생성 API 마련 |
| 리포트 근거 | 실제 실행 코드, 텍스트 출력, 표와 수치 |
| 리포트 내용 | 생산라인 특이사항 중심. 배치별 작성 지침 입력은 제외 |
| 리포트 형식 | Markdown 파일 저장 및 결과 노트북 마지막에 추가 |
| 리포트 저장 | Executor의 Artifact API 사용 |
| 리포트 실패 | 코드 재실행 없이 리포트 단계만 재시도 |
| 이미지 | 출력 이미지는 보존. 초기 VLM 없음. 추후 모델 지원 시 해석 확장 |
| 원본 저장 | 공유 PV 사용 |
| 데이터 저장 | PostgreSQL 사용 가능. Redis는 사용 목적이 있어야 도입 |
| 결과 제공 | 접근 가능한 노트북 URL 또는 Executor 다운로드 API 활용 |
| 보관 | 원본·버전·실행 이력·결과 자동 삭제 없음 |
| 알림 | 초기 메일·메신저 알림 제외 |
| 규모 | 분석 시스템 초기 사용자 100~200명. 배치 수·실행량은 미정 |

## 초기 범위에서 제외

- 배치 전용 프론트엔드와 프로젝트별 배치 관리.
- 노트북 간 DAG, 선행 작업 조건, 매개변수 주입.
- 임의 노트북의 Markdown·raw 셀 레이아웃 보존.
- 배치별 프롬프트 편집, 이미지에만 있는 정보의 분석.
- 이전 실행과의 자동 비교, 새 분석 코드 생성·수정·추가 실행.
- 자동 삭제, 알림, 배치가 직접 수행하는 런타임 관리.

공휴일 달력, 영업일 보정, 외부 이벤트 트리거는 초기 요구사항으로 확정하지 않았다.
일정 종류와 표현식의 구체 범위는 설계 초안에 별도로 명시한다.

## 구현 전 확인할 사항

1. Executor 자동 재시도 정책은 추후 결정하며 초기 등록 구현을 막지 않음.
2. 서비스 간 인증 방식과 검증된 사용자 정보 전달 계약.
3. 공유 PV 입력·결과 루트, UID/GID, 읽기·쓰기 권한.
4. 지원 커널 목록과 사용자 코드의 데이터·라이브러리 접근 환경.
5. 업로드 크기·셀 수, 대기 수, 동시 실행 수, 보충 실행 제한값.

이 항목들은 확정 기능을 뒤집는 사항이 아니라 배포 환경과 연동 계약의 결정 사항이다.
